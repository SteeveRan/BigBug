# User Stories: Git Mirroring

User stories модуля Git Mirroring: зеркалирование репозиториев GitHub в GitLab, поддержание актуальности, проверка целостности и восстановление после расхождений. Персоны — платформенные роли: admin, operator, viewer.

Потоки — в [use cases](../use-cases/git-mirroring.md); поверхность отказов — в [edge cases](../edge-cases/git-mirroring.md). Отчёты по зеркалам — отдельный модуль (issue #166): story US-gitmrr-009 покрывает только видимость журналов конкретного зеркала, но не страницы Reports.

## US-gitmrr-001: Импортировать группу источников из Git-провайдера

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-001 |
| Название | Импортировать группу источников из Git-провайдера |
| Персона | operator |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — источники |
| Оценка | 3 points |

### User Story Statement

**Как** operator,

**я хочу** импортировать GitHub-группу (организацию) со всеми её репозиториями одним действием,

**чтобы** зарегистрировать весь источник целиком вместо ввода репозиториев по одному.

### Context & Background

Зеркалирование начинается с инвентаря источников. GitHub-организация может содержать десятки репозиториев; ручной ввод не масштабируется. Платформа должна разрешить группу через настроенный Resource Provider и зарегистрировать её репозитории как source repositories (поток: UC-gitmrr-001).

### Acceptance Criteria

#### AC-1: Импорт по идентификатору группы

**Дано** существует Git-провайдер с валидными credentials

**Когда** я отправляю импорт с указанием провайдера и идентификатора группы

**Тогда** система регистрирует группу и все репозитории, видимые этим credentials, и сообщает число зарегистрированных

#### AC-2: Состояние импорта видно

**Дано** импорт завершился успешно

**Когда** я открываю страницу Sources

**Тогда** импортированная группа и её репозитории присутствуют в списке

#### AC-3: Refresh перечитывает источник

**Дано** импортированная группа существует

**Когда** я запускаю refresh

**Тогда** система перечитывает список репозиториев у провайдера и отражает появившиеся и исчезнувшие репозитории

### Technical Notes

- Импорт требует `source_groups:write`; список/детали — `source_groups:read`; refresh — `source_groups:refresh`.
- Получение метаданных репозиториев идёт в фоне после регистрации; список не должен блокироваться на нём.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| Resource Provider с GitHub credentials | Feature | Ready |

### Out of Scope

- Выбор подмножества репозиториев при импорте (импорт — всё-или-отчёт)
- Автоматический повторный импорт по расписанию

## US-gitmrr-002: Создать зеркало для source-репозитория

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-002 |
| Название | Создать зеркало для source-репозитория |
| Персона | operator |
| Приоритет | P0 |
| Epic/Feature | Git Mirroring — зеркала |
| Оценка | 3 points |

### User Story Statement

**Как** operator,

**я хочу** создать зеркало, связывающее source-репозиторий с целевым GitLab-проектом,

**чтобы** платформа могла поддерживать цель в актуальном состоянии относительно источника.

### Context & Background

Зеркало — центральная запись модуля. Его создание должно давать зеркало, готовое к sync: целевой GitLab-проект должен существовать и быть привязан к зеркалу в момент создания. Зеркало, которое не может синхронизироваться из-за непривязанной цели — полуфабрикат: система обязана либо провести оператора через привязку как часть создания (поток: UC-gitmrr-002), либо явно пометить зеркало как не-готовое-к-sync (edge cases EC-gitmrr-008..010).

### Acceptance Criteria

#### AC-1: Зеркало привязано к существующей цели

**Дано** source-репозиторий и существующий GitLab-проект (созданный через модуль GitLab Projects)

**Когда** я создаю зеркало, выбирая source-репозиторий и целевой проект

**Тогда** система сохраняет зеркало с привязанным целевым проектом и статусом Pending

#### AC-2: Создание без привязанной цели — явное

**Дано** целевой GitLab-проект не привязан при создании

**Когда** я создаю зеркало

**Тогда** система сохраняет зеркало со статусом, который однозначно означает «цель ещё не привязана» — не generic Pending — и показывает на зеркале, чего не хватает до первого успешного sync

#### AC-3: Первый sync непривязанного зеркала объясняет пробел

**Дано** зеркало без привязанного целевого проекта

**Когда** предпринимается sync (вручную или по расписанию)

**Тогда** система отклоняет запуск с сообщением, называющим недостающее предусловие, и ссылкой на место, где целевой проект можно создать или привязать

#### AC-4: Дубликат источника — предупреждение, не блокировка

**Дано** другое активное зеркало уже ссылается на тот же source-репозиторий

**Когда** я создаю зеркало для него

**Тогда** система показывает предупреждение о дубликате, записывает его в audit log и всё равно создаёт зеркало по подтверждению

### Technical Notes

- Создание зеркала требует `mirrors:write`.
- Sync engine не выполняет git-операций сам; он триггерит CI-пайплайн целевого проекта (ADR-0008). Привязанный id целевого проекта — жёсткое предусловие каждого sync.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-001 (инвентарь источников) | Story | Ready |
| Модуль GitLab Projects (создание целевого проекта) | Module | Ready |

### Out of Scope

- Автоматическое создание GitLab-проекта при создании зеркала (решение — в grill #142)

## US-gitmrr-003: Массово создать зеркала

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-003 |
| Название | Массово создать зеркала |
| Персона | operator |
| Приоритет | P2 |
| Epic/Feature | Git Mirroring — зеркала |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу** создавать зеркала для многих source-репозиториев одним действием,

**чтобы** подключение крупной source-группы не превращалось в десятки повторов диалога создания.

### Context & Background

Source-группы регулярно превышают 50 репозиториев. Массовое создание обязано валидировать весь батч заранее и отчитываться по-элементно (поток: UC-gitmrr-003).

### Acceptance Criteria

#### AC-1: Батч до 500

**Дано** до 500 source-репозиториев

**Когда** я отправляю массовое создание

**Тогда** система создаёт по зеркалу на элемент в одном запросе

#### AC-2: Превышение лимита отклоняется заранее

**Дано** батч больше 500

**Когда** я его отправляю

**Тогда** система отклоняет запрос целиком с сообщением о лимите и не создаёт ничего

#### AC-3: Несуществующие источники перечислены

**Дано** батч ссылается минимум на один неизвестный source-репозиторий

**Когда** я его отправляю

**Тогда** система отклоняет запрос, перечисляя неизвестные идентификаторы, и не создаёт ничего

### Technical Notes

- Требует `mirrors:write`. Семантика дубликата — как в US-gitmrr-002 AC-4 (advisory).

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |

### Out of Scope

- Режим частичного успеха (всё-или-ничего в рамках запроса)

## US-gitmrr-004: Запустить sync зеркала вручную

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-004 |
| Название | Запустить sync зеркала вручную |
| Персона | operator |
| Приоритет | P0 |
| Epic/Feature | Git Mirroring — sync |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу** триггерить sync зеркала немедленно,

**чтобы** актуализировать цель, не дожидаясь расписания (например, сразу после релиза).

### Context & Background

Sync переносит код триггером CI-пайплайна целевого GitLab-проекта (ADR-0008). Оператор триггерит; пайплайн исполняется; результат возвращается асинхронно (US-gitmrr-008). Поток: UC-gitmrr-004.

### Acceptance Criteria

#### AC-1: Триггер принят, запуск записан

**Дано** зеркало с привязанной целью и настроенным пайплайном на его sync-группе

**Когда** я триггерю sync

**Тогда** система записывает запись sync-ранa, помечает зеркало In Progress и возвращает успех

#### AC-2: Ошибка конфигурации — именованная

**Дано** у sync-группы зеркала не настроен пайплайн

**Когда** я триггерю sync

**Тогда** система записывает skipped-ран с причиной «no pipeline configured» и показывает это на зеркале

#### AC-3: Результат виден

**Дано** запущенный sync завершился на стороне GitLab

**Когда** я смотрю зеркало

**Тогда** я вижу исход sync (completed/failed) и его временную метку

### Technical Notes

- Требует `mirrors:sync`. Триггер freshness использует то же право.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |
| US-gitmrr-005 (пайплайн привязан к группе) | Story | Ready |

### Out of Scope

- Стриминг прогресса во время исполнения пайплайна (статус обновляется по событиям завершения)

## US-gitmrr-005: Настроить автоматический sync через sync-группу

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-005 |
| Название | Настроить автоматический sync через sync-группу |
| Персона | operator |
| Приоритет | P0 |
| Epic/Feature | Git Mirroring — sync-группы |
| Оценка | 3 points |

### User Story Statement

**Как** operator,

**я хочу** настроить cron-расписание и лимит конкурентности на sync-группе,

**чтобы** все зеркала группы поддерживались актуальными автоматически без настройки каждого, а API источника не перегружался.

### Context & Background

Sync-группа — единица расписания (ADR-0008): cron-строки для sync и freshness, лимиты конкурентности, включение/выключение. Изменение расписания должно вступать в силу без редеплоя или рестарта платформы (поток: UC-gitmrr-006).

### Acceptance Criteria

#### AC-1: Cron-расписание гоняет запуски

**Дано** sync-группа с включённым sync-cron

**Когда** cron срабатывает

**Тогда** система синхронизирует зеркала группы в пределах настроенного лимита конкурентности

#### AC-2: Изменение расписания действует без рестарта

**Дано** sync-группа, чей cron или флаг включённости я только что изменил

**Когда** наступает следующий cron-момент

**Тогда** запуски следуют новой конфигурации — без рестарта приложения между делом

#### AC-3: Выключенная группа не запускается

**Дано** выключенная sync-группа

**Когда** её cron-момент проходит

**Тогда** sync-запуски для её зеркал не стартуют

#### AC-4: Невалидный cron отклоняется при сохранении

**Дано** я ввожу некорректное cron-выражение (или строку длиннее лимита 100 символов)

**Когда** я сохраняю sync-группу

**Тогда** система отклоняет изменение с ошибкой по полю и сохраняет прежнее расписание

#### AC-5: Зеркала назначаются в группу массово

**Дано** до 100 зеркал

**Когда** я массово назначаю их в sync-группу

**Тогда** все перечисленные зеркала принадлежат этой группе; зеркала из других групп перемещаются

### Technical Notes

- `sync_groups:read/write/delete`; массовое назначение ≤ 100 за запрос; удаление default-группы запрещено, зеркала удаляемой группы мигрируют в default.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |
| US-gitmrr-002 (пайплайн привязан к группе) | Story | Ready |

### Out of Scope

- Per-mirror cron-переопределения (единица расписания — группа)

## US-gitmrr-006: Проверить свежесть зеркала

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-006 |
| Название | Проверить свежесть зеркала |
| Персона | operator |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — здоровье |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу** дешёвую ручную проверку свежести — сравнение источника с целью,

**чтобы** видеть, отстаёт ли зеркало от источника, не запуская полный sync.

### Context & Background

Freshness сравнивает последнее известное состояние коммита источника с записанным (ADR-0008). Проверка дешёвая — безопасно запускать часто, вручную и по расписанию. Поток: UC-gitmrr-007.

### Acceptance Criteria

#### AC-1: Вердикт — один из трёх

**Дано** зеркало со связанным source-репозиторием

**Когда** я запускаю freshness-проверку

**Тогда** система записывает результат FRESH, STALE или ERROR с временной меткой

#### AC-2: STALE виден на зеркале

**Дано** freshness-проверка вернула STALE

**Когда** я смотрю список или детали зеркала

**Тогда** зеркало несёт warning-состояние, учёт расшедшихся коммитов обновлён

#### AC-3: Непроверяемый источник — ERROR, не подделка

**Дано** провайдер источника недоступен или credentials невалидны

**Когда** я запускаю freshness-проверку

**Тогда** система записывает ERROR с причиной провайдера; прежнее состояние зеркала не подменяется фальшивым FRESH

### Technical Notes

- Требует `mirrors:sync` (как и ручной sync).

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |

### Out of Scope

- Автоматическое исправление при STALE (оператор сам решает перезапустить sync)

## US-gitmrr-007: Проверить целостность зеркала

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-007 |
| Название | Проверить целостность зеркала |
| Персона | operator |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — здоровье |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу** сравнить HEAD-коммиты источника и цели, обнаруживая ручные изменения в цели,

**чтобы** доверять зеркалу как точной копии и вовремя замечать дрейф цели.

### Context & Background

Зеркало существует, чтобы ему доверяли. Integrity check — прямое сравнение HEAD (ADR-0008) с вердиктами MATCH / MISMATCH / ERROR. Операция читает внешнее состояние, но чувствительна — охраняется собственным правом. Поток: UC-gitmrr-008.

### Acceptance Criteria

#### AC-1: Вердикт — один из трёх

**Дано** зеркало с привязанным целевым проектом

**Когда** я запускаю integrity check

**Тогда** система записывает MATCH, MISMATCH или ERROR в журнал зеркала и соответственно обновляет его состояние

#### AC-2: MISMATCH виден и посчитан

**Дано** integrity check вернул MISMATCH

**Когда** я смотрю зеркало

**Тогда** зеркало показывает warning-состояние с увеличенным счётчиком расшедшихся коммитов

#### AC-3: Право проверяется

**Дано** пользователь без права integrity-check

**Когда** он предпринимает операцию

**Тогда** система отклоняет её с 403 — эндпоинт не открыт любому аутентифицированному

### Technical Notes

- Целевое право `mirrors:integrity_check` (засеяно; admin+operator). Текущий код его не проверяет — расхождение зафиксировано в edge cases (EC-gitmrr-018) и grill #139 (C3).

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |

### Out of Scope

- Автоматический integrity-режим по расписанию (запуски — пользовательские или групповые)

## US-gitmrr-008: Отслеживать результаты sync зеркала

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-008 |
| Название | Отслеживать результаты sync зеркала |
| Персона | viewer |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — наблюдаемость |
| Оценка | 2 points |

### User Story Statement

**Как** viewer,

**я хочу** видеть статус и историю sync-запусков зеркала,

**чтобы** отвечать на вопрос «зеркало актуально? что было в последнем запуске?» без обращения к operator.

### Context & Background

Каждая операция sync, freshness и integrity оставляет запись в журнале (ADR-0008). Событие завершения пайплайна обязано финализировать состояние зеркала — зеркало не должно оставаться In Progress после завершения его пайплайна (поток: UC-gitmrr-005; разрыв разобран в grill #142, H4).

### Acceptance Criteria

#### AC-1: Терминальные состояния достижимы

**Дано** sync-запуск завершился (успех или провал на стороне GitLab)

**Когда** событие завершения обработано

**Тогда** статус зеркала отражает исход — оно никогда не остаётся In Progress бесконечно

#### AC-2: История просматривается

**Дано** зеркало с прошлыми операциями

**Когда** я открываю его журнал

**Тогда** я вижу хронологический список запусков с типом, исходом и временными метками

#### AC-3: Audit-след есть

**Дано** sync завершился или провалился

**Когда** я смотрю audit log

**Тогда** соответствующее audit-событие записано

### Technical Notes

- Чтение требует `mirrors:read`.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-004 | Story | Ready |

### Out of Scope

- Страницы Reports (отдельный модуль, issue #166)

## US-gitmrr-009: Обнаружить осиротевшие GitLab-проекты

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-009 |
| Название | Обнаружить осиротевшие GitLab-проекты |
| Персона | admin |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — orphaned |
| Оценка | 2 points |

### User Story Statement

**Как** admin,

**я хочу** находить GitLab-проекты на управляемых целевых инстансах, на которые не ссылается ни одно зеркало,

**чтобы** замечать расхождение между записями платформы и реальностью в GitLab.

### Context & Background

Orphaned discovery — отчёт по требованию над целевыми GitLab-инстансами: проекты, чьи id не ссылается ни одно активное зеркало (ADR-0008). Discovery только сообщает; исправление — отдельная story, переданная #160 (US-gitmrr-010, moved). Поток: UC-gitmrr-009 (шаги 1–2).

### Acceptance Criteria

#### AC-1: Осиротевшие перечислены

**Дано** целевой GitLab-инстанс с проектами, на которые не ссылаются зеркала

**Когда** я запускаю discovery

**Тогда** каждый проект без ссылки перечислен с путём, web URL и временем обнаружения

#### AC-2: Право проверяется

**Дано** пользователь без права управления orphaned

**Когда** он предпринимает discovery

**Тогда** система отклоняет с 403

#### AC-3: «Нет провайдеров» — действенный стейт, не generic-сбой

**Дано** ни одного активного GitLab-провайдера не настроено

**Когда** я открываю orphaned-страницу или запускаю discovery

**Тогда** система показывает действенный empty state («настройте GitLab-провайдера») со ссылкой в настройки провайдеров — не generic-ошибку загрузки

#### AC-4: Один сбойный провайдер не валит скан

**Дано** два GitLab-провайдера, один недоступен

**Когда** я запускаю discovery

**Тогда** доступный провайдер всё равно просканирован и его результаты возвращены; сбойный перечислен отдельно

### Technical Notes

- Целевое право `mirrors:manage_orphaned` (засеяно; admin). Текущий код охраняет только аутентификацией — расхождение зафиксировано (EC-gitmrr-019), гриллы #139 (C3) / #140 (H2).

## US-gitmrr-010: Перепривязать или удалить осиротевшее зеркало

| Название | Перепривязать или удалить осиротевшее зеркало |
| Персона | admin |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — orphaned |
| Оценка | 3 points |

### User Story Statement

**Как** admin,

**я хочу** перепривязать запись зеркала на другой целевой путь или удалить протухшую orphan-запись,

**чтобы** разрешать осиротевшие записи в платформе, а не правками в БД.

### Context & Background

UI предлагает relink (reassign/move target) и delete для orphaned-зеркал, но backend-эндпоинты не существуют — поток обрывается гарантированной ошибкой (audit C4, grill #140). Story фиксирует требуемое поведение: операции исправления обязаны существовать на границе платформы, быть под проверкой прав и давать явное подтверждение на разрушающие шаги (поток: UC-gitmrr-009, шаги 3–4).

### Acceptance Criteria

#### AC-1: Операции relink существуют end-to-end

**Дано** orphaned-запись зеркала

**Когда** я переназначаю её в другую sync-группу или перемещаю целевой путь

**Тогда** операция успешно проходит на границе платформы и запись зеркала отражает изменение

#### AC-2: Удаление подтверждается и обратимо

**Дано** orphaned-запись зеркала

**Когда** я удаляю её с явным подтверждением

**Тогда** запись зеркала мягко удаляется (восстановимо в retention-окно), а сам GitLab-проект не затрагивается никогда

#### AC-3: Права проверяются на каждом действии

**Дано** пользователь с правами только на чтение

**Когда** он предпринимает любое relink/delete-действие

**Тогда** система отклоняет его с 403

### Technical Notes

- Действия под `mirrors:write` (relink) и `mirrors:delete` (delete) — соответствует текущему PermissionGate на фронте. Имплементация — в grill #140.

### Out of Scope

- Автоматическое (без участия человека) исправление осиротевших — всегда действие человека (non-goal ADR-0008)

## US-gitmrr-011: Удалять и восстанавливать зеркала безопасно

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-011 |
| Название | Удалять и восстанавливать зеркала безопасно |
| Персона | operator |
| Приоритет | P1 |
| Epic/Feature | Git Mirroring — жизненный цикл |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу**, чтобы удаление зеркала было обратимым soft delete с retention-окном, а целевой GitLab-проект переживал его,

**чтобы** случайное удаление ничего не стоило, а cleanup никогда не разрушал данные в GitLab.

### Context & Background

Удаление — мягкое, с retention-окном (настройка `soft_delete_retention_days`, дефолт 30 дней); ежедневный cleanup физически удаляет истекшие записи в FK-порядке и никогда не трогает GitLab-проекты (ADR-0008). Поток: UC-gitmrr-010.

### Acceptance Criteria

#### AC-1: Soft delete обратим

**Дано** удалённое зеркало в пределах retention-окна

**Когда** я восстанавливаю его

**Тогда** зеркало и его каскадно удалённый source-репозиторий снова активны

#### AC-2: Целевой проект переживает удаление

**Дано** я удаляю зеркало (мягко или по истечении retention)

**Когда** cleanup удаляет запись

**Тогда** целевой GitLab-проект не изменяется и не удаляется

#### AC-3: Retention соблюдается

**Дано** зеркало мягко удалено дольше retention-периода

**Когда** ежедневный cleanup запускается

**Тогда** запись физически удаляется, а удаление зафиксировано в audit log

### Technical Notes

- Удаление/восстановление требуют `mirrors:delete`.
- Retention-окно — настройка деплоя (`soft_delete_retention_days`, дефолт 30 дней); аналитика требует наличия окна и его соблюдения — конкретное значение является конфигурацией, а не требованием.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |

### Out of Scope

- Настройка retention-периода per-деплой (единая платформенная настройка)

## US-gitmrr-012: Усыновить существующий GitLab-проект как зеркало

### Story Header

| Поле | Значение |
|-------|-------|
| ID | US-gitmrr-012 |
| Название | Усыновить существующий GitLab-проект как зеркало |
| Персона | operator |
| Приоритет | P2 |
| Epic/Feature | Git Mirroring — жизненный цикл |
| Оценка | 2 points |

### User Story Statement

**Как** operator,

**я хочу** зарегистрировать GitLab-проект, уже получающий код из другого места, как управляемое зеркало,

**чтобы** существующие настройки зеркалирования перешли под управление платформы без пересоздания.

### Context & Background

Импорт регистрирует зеркало с начальным состоянием OK и фиксирует последний известный коммит источника. Импорт обязан давать ту же sync-готовую привязку, что и US-gitmrr-002 — включая привязку целевого проекта (edge cases EC-gitmrr-010..012).

### Acceptance Criteria

#### AC-1: Усыновлённое зеркало отслеживается

**Дано** существующий GitLab-проект и его GitHub-источник

**Когда** я импортирую его как зеркало

**Тогда** зеркало зарегистрировано со состоянием OK и последним известным коммитом источника

#### AC-2: Импорт без привязанной цели — явный

**Дано** усыновлённый проект невозможно привязать к записи целевого проекта

**Когда** импорт завершается

**Тогда** зеркало помечено статусом не-готово-к-sync по US-gitmrr-002 AC-2 — не молчаливым OK

### Technical Notes

- Требует `mirrors:import`.

### Dependencies

| Зависимость | Тип | Статус |
|------------|------|--------|
| US-gitmrr-002 | Story | Ready |

### Out of Scope

- Автоматическое обнаружение пригодных к усыновлению проектов
