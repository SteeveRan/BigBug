# Security — реагирование на утечки секретов и работа с gitleaks

Операционный гайд для разработчиков и агентов: что делать при обнаружении утечки credential в git. Архитектурное решение (инструмент, точки принуждения, политика) — [ADR-0032](../adr/common/0032-adopt-gitleaks-secret-scanning.md).

## Enforcement points (gitleaks)

| Точка | Как работает | Когда |
|---|---|---|
| Pre-commit hook | `.pre-commit-config.yaml`, официальный gitleaks hook, **staged-only** — быстро | Каждый локальный коммит |
| GitHub Actions | `.github/workflows/gitleaks.yml` (gitleaks-action), blocking | push, PR, weekly cron, вручную (workflow_dispatch) |
| `make secrets-scan` | `gitleaks detect --full-history` | On-demand: baseline, расследования |

Weekly cron и `make secrets-scan` сканируют полную историю. Tooling: [#72](https://github.com/SteeveRan/BigBug/issues/72), [#73](https://github.com/SteeveRan/BigBug/issues/73), [#74](https://github.com/SteeveRan/BigBug/issues/74).

## Процедура реагирования на утечку

**Принципы** (зафиксированы в ADR-0032):

1. **Ротация/отзыв credential — обязательна.** Скомпрометированный секрет нейтрализуется только во внешней системе; в git он останется в любом случае (клоны, форки, кэш CI).
2. **Git-история по умолчанию НЕ переписывается.** Rewrite ломает всех worktree-агентов и collaborators и сам по себе не отзывает секрет. Это last resort — см. ниже.

### Шаги

1. **Подтвердите находку.** `gitleaks detect --full-history` (или `make secrets-scan`) покажет commit, файл, строку. Определите: реальный секрет или false positive (см. «Работа с allowlist»).
2. **Ротируйте/отзовите секрет во внешней системе.** Создайте новый credential, обновите его в источнике (`.env`, provider settings в BigBug, k8s Secret), отзовите старый. **Это шаг «стоп всё» — делается до любого разбора, откуда утекло.** Если секрет мог использовать кто-то ещё (общие PAT, сервисные учётки), проверьте и остальные системы, где он валиден.
3. **Проверьте, не использовал ли секрет кто-то посторонний.** Audit logs / activity log внешней системы за период от попадания в git до ротации: неожиданные запросы, логины, созданные токены.
4. **Удалите секрет из рабочего кода.** Замените на загрузку из env / secrets manager; секрет не должен читаться в файлах, попадающих в git. Задокументируйте, где секрет теперь живёт.
5. **Подтвердите, что finding разрешён.** `make secrets-scan` по-прежнему находит секрет в истории — это ожидаемо (история не переписывается). Разрешённым finding считается, когда секрет **отозван и невалиден**, а из рабочего кода удалён. Зафиксируйте в issue/заметке: что утекло, когда, когда ротировано, кто проверял логи.
6. **(Только по решению владельца проекта)** — переписывание истории. Применяется как отдельное скоординированное действие, если: секрет попал в публичный/широкий доступ без возможности ротации, или требование регулирующего органа. Все агенты останавливаются, worktree синхронизируются заново, force-push координируется вручную.

### Когда история переписывается / не переписывается

| Ситуация | Действие |
|---|---|
| Секрет ротирован и невалиден | История не трогается — риск устранён ротацией |
| Секрет отозвать невозможно (например, чужой/унаследованный) | Оценить exposure → как правило, переписывание + принудительная смена всех зависимых credential |
| Регуляторное требование удалить секрет из истории | Переписывание, скоординированно |

## Работа с allowlist

False positives убираются **только** в `.gitleaks.toml` (path-based allowlist + `stopwords`). Inline-маркеры `gitleaks:allow` в исходниках запрещены (ADR-0032).

* **Фейковый токен в новом файле под `docs/` или в тестовой фикстуре** — обычно уже покрыто allowlist'ом; проверьте, что путь попадает под существующие правила.
* **Нужен новый allowlist-паттерн** — добавьте его в `.gitleaks.toml` отдельным коммитом с обоснованием в commit message. Изменения `.gitleaks.toml` ревьюятся особенно внимательно: allowlist — место, где реальный секрет можно спрятать.
* **Finding на реальный секрет** — не глушить allowlist'ом: ротировать по процедуре выше, затем убрать секрет из кода.

## Bypass pre-commit hook

`git commit --no-verify` обходит локальный хук. Это **легитимный emergency-exit**, когда хук блокирует срочный фикс, но:

* CI всё равно просканирует push — утечка будет замечена;
* обход хука осознанным образом оставляет утечку в истории — дальше по процедуре реагирования выше.
